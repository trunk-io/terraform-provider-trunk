# trunk_merge_queue (Resource)

Manages a Trunk merge queue: one per repository and target branch.

Only the settings in your configuration are managed. A setting you leave out keeps whatever value the queue has, including one set in the Trunk app.

Apply doesn't take over an existing queue: [import](#import) it first.

Not managed by this provider: allowed bot submitters, Slack notifications, and impacted targets from fork PRs. Set those in the Trunk app.

With an API key, the v2 API caps some values (for example `concurrency` at 1000 and `not_ready_timeout_hours` at 720); an apply above a cap fails.

## Example Usage

```terraform
resource "trunk_merge_queue" "main" {
  repo = {
    host  = "github.com"
    owner = "my-org"
    name  = "my-repo"
  }
  target_branch = "main"

  mode         = "parallel"
  concurrency  = 10
  merge_method = "squash"

  batch                          = true
  batching_min_size              = 4
  batching_max_wait_time_minutes = 10
  batching_rules = [
    { target_pattern = "//db/migrations:*", policy = "isolate" },
  ]

  required_statuses = ["build", "test"]
}
```

## Changing settings outside Terraform

A change made in the Trunk app or through the API to a setting in your configuration shows up in the next plan, and apply reverts it. A change to a setting you left out is kept. With an API key, `managed_state` reads `terraform_with_drift` after either, until the next apply that changes the queue.

## Switching modes

Changing `mode` on an existing queue starts a switch: the queue drains (new pull requests wait) and switches once it is empty. Until then Terraform shows the new mode and refuses any change to the queue, since changing its state would abandon the switch. Further changes wait until the switch finishes. To cancel a switch, use the Trunk app, then set `mode` back in your configuration, or the next apply starts the switch again.

## Deleting a queue

A queue that still has pull requests can't be deleted. Set `state = "draining"`, apply, and destroy once the queue is empty.

## Schema

### Required

- `repo` (Attributes) The repository the queue belongs to. Changing it replaces the queue. (see [below for nested schema](#nestedatt--repo))
- `target_branch` (String) The branch the queue merges into. Changing it replaces the queue.

### Optional

- `batch` (Boolean) Test several pull requests together as one batch.
- `batching_max_wait_time_minutes` (Number) Minutes to wait for a batch to reach `batching_min_size` before testing it anyway. `0` doesn't wait (needs an API key; v1 requires at least 1).
- `batching_min_size` (Number) Target batch size: how many pull requests a batch waits for, and the most it holds.
- `batching_rules` (Attributes Set) Rules that change how pull requests are batched based on the build targets they impact. Only applies in `parallel` mode with impacted targets uploaded. Set to `[]` to remove every rule. (see [below for nested schema](#nestedatt--batching_rules))
- `bisection_concurrency` (Number) How many tests bisecting a failed batch may run at once, separate from `concurrency`.
- `can_optimistically_merge` (Boolean) When a pull request passes before those ahead of it finish testing, merge it and them together, since its tests included their changes.
- `commands_enabled` (Boolean) Accept `/trunk` commands in pull request comments.
- `comments_enabled` (Boolean) Post comments on pull requests about their progress through the queue.
- `concurrency` (Number) How many pull requests (or batches) the queue tests at once.
- `create_prs_for_testing_branches` (Boolean) Create a draft pull request for each test branch, so pull-request CI runs on it. When false, CI must run on pushes to `trunk-merge/` branches.
- `direct_merge_mode` (String) `always` merges a pull request right away when it is already based on the tip of the target branch, the queue is empty and its tests passed; `off` always tests it in the queue.
- `enqueueing_label` (String) The GitHub label that enqueues a pull request when `label_commands_enabled` is true.
- `extension_enabled` (Boolean) Show the Trunk browser extension's merge queue controls on pull requests into this branch.
- `label_commands_enabled` (Boolean) Let a GitHub label enqueue a pull request, and removing it dequeue it (see `enqueueing_label`).
- `merge_method` (String) How pull requests are merged: `merge_commit`, `squash`, or `rebase`.
- `mode` (String) `single` tests pull requests in one line, each with the changes ahead of it. `parallel` splits the queue into independent lines by impacted targets, which CI must upload. Changing it on an existing queue starts a mode switch.
- `not_ready_timeout_hours` (Number) Hours a submitted pull request may stay unable to enter the queue before it is cancelled (**Stale PR Timeout** in the app). `0` means no timeout.
- `optimization_mode` (String) `bisection_skip_redundant_tests` (**Skip Redundant Bisection Tests** in the app): while bisecting a failed batch, skip any set of pull requests that already failed in the same bisection. `off` tests every set.
- `pending_failure_depth` (Number) How many levels of later test runs to wait for before failing a pull request (or bisecting its batch). With `can_optimistically_merge`, a later run that passes clears a failure caused by a flaky test. `0` doesn't wait.
- `required_statuses` (Set of String) The checks a pull request's tests must pass, overriding `.trunk/trunk.yaml` and branch protection. Set to `[]` to remove the override and use those again; an override can't be empty. Leave it out to leave the queue's override as it is.
- `state` (String) `running`, `paused` (starts no new tests and merges nothing), or `draining` (tests and merges the pull requests already in the queue). Pull requests submitted while paused or draining wait until it's running.
- `state_labels_enabled` (Boolean) Label pull requests with their merge queue state.
- `status_check_enabled` (Boolean) Post a GitHub check on queued pull requests.
- `test_branch_construction_mode` (String) How the queue creates the `trunk-merge/` branch it tests on. `rename_temp_branch` builds it on a `trunk-temp/` branch and renames it. `push_new_branch_from_temp` creates it directly; use it when a GitHub ruleset on `trunk-temp/` branches blocks renaming them.
- `testing_timeout_minutes` (Number) Minutes to wait for a pull request's tests before failing it. `0` means no timeout.

### Read-Only

- `id` (String) The queue's address, `{host}/{owner}/{name}/{target_branch}`.
- `managed_state` (String) Whether the queue is managed by Terraform: `manual`, `terraform`, or `terraform_with_drift` (changed outside Terraform since the last apply). Only the v2 API reports it; null with an organization API token.
- `queue_id` (String) The queue's v2 ID. Null with an organization API token.

## Import

```shell
# By repository and target branch. Branch names may contain slashes.
terraform import trunk_merge_queue.main github.com/my-org/my-repo/main

# Or, with an API key, by the queue's v2 ID.
terraform import trunk_merge_queue.main xK9mP2nQ
```

A queue's ID is its `queue_id`, or its `id` in the v2 API. Importing by ID records the repository as Trunk spells it. If your configuration's `repo` differs in capitals, import by path instead, or the plan replaces the queue.
